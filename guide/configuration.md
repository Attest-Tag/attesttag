# Configuration

Configuration comes from two places. **Environment variables**, loaded from the dotenv file named
by `ENV_FILE` (`.env.testing` locally), hold secrets, paths and defaults. **Console settings** are
stored in the database, edited on the Settings page or via `PUT /api/settings`, take effect
without a restart, and override the corresponding environment default.

## Environment variables

Grouped the way you meet them: the first table is what a deployment cannot start without, then
email, which it can do without, then the key to back up, and everything below that has a working
default. [`.env.example`](../.env.example) lists most of them as a commented file, and
[`deploy/env/selfhost.env.example`](../deploy/env/selfhost.env.example) is the short list a
self-hosted deployment starts from.

### Required

| variable | default | purpose |
|---|---|---|
| `SLACK_SIGNING_SECRET` | required | Slack App Credentials signing secret; verifies HTTP events and interactions before parsing. No `SLACK_APP_TOKEN` is needed. Each workspace's bot token still arrives from its OAuth install and is stored sealed; a `SLACK_BOT_TOKEN` left set is ignored, with a warning at startup |
| `SLACK_CLIENT_ID`, `SLACK_CLIENT_SECRET` | required | Connecting a Slack workspace, and Sign in with Slack. Without them nothing can be connected |
| `OPENROUTER_API_KEY` or `LLM_API_KEY` | required | model provider key (`LLM_API_KEY` wins when both are set). A value exported in the shell beats the dotenv file, and the bot warns at startup with both fingerprints |

### Email (optional)

Nothing here is required to start. Without a key the bot logs each message rather than sending
it — and, in the container image and on Cloud Run, warns once at startup — and the console hands
out verification and invitation links to copy instead of promising an inbox, so a deployment with
no mail provider still works, it just makes an admin the delivery mechanism.

| variable | default | purpose |
|---|---|---|
| `RESEND_API_KEY` | optional, strongly recommended | Transactional email. Verification, password resets and invitations all go by email, so a deployment without it can lock people out of their own accounts — but it is never a refusal to start (the container image and Cloud Run warn at startup): the mailer degrades to logging who would have been written to, and the console offers the link to copy by hand instead of promising an inbox. Any non-empty value is taken as a key, so leave it unset rather than holding a placeholder |
| `MAIL_FROM` | required with the key | The From address, e.g. `attest_tag <no-reply@mail.example.com>`. Its domain must be verified at resend.com/domains with the SPF and DKIM records it gives you added to DNS. Set the key without this and mail stays off, with a warning saying so |

### The key to back up

| variable | default | purpose |
|---|---|---|
| `MASTER_KEY` | generated by a bare binary; required in a container | base64 of 32 random bytes (`openssl rand -base64 32`; a hex key is refused), sealing credentials and signing Configure links. A bare binary that finds none generates one and appends it to the dotenv file it read. The container image and Cloud Run refuse to start instead, because nothing there would keep it: a key minted on every start loses whatever was sealed under the last one. **Back it up somewhere else**: it seals Slack bot tokens, connection secrets, per-user OAuth tokens and TOTP secrets, and without it every one of them has to be reconnected by hand |
| `MASTER_KEY_PREVIOUS` | unset | the old key during a rotation: set it here, the new one in `MASTER_KEY`, deploy, and remove it once nothing sealed under the old key remains. A value moves to the new key only when it is written again (a refreshed OAuth token, a reinstalled workspace, a re-entered secret), and nothing reports how many are left. Configure links, connect links and operator sign-ins are signed with the current key alone, so ones issued before the switch stop working |
| `REQUIRE_MASTER_KEY` | `1` in the container image, else unset | refuse to start without `MASTER_KEY` rather than generate one. It also ignores `LLM_DUMP_DIR`, keeps session cookies Secure on every origin unless `INSECURE_COOKIES=1`, and warns at startup when `RESEND_API_KEY` is unset. Cloud Run behaves the same without it |

### Storage and knowledge

| variable | default | purpose |
|---|---|---|
| `DATABASE_URL` | unset | `postgres://user:pass@host:5432/attesttag?sslmode=require`. Set it and the deployment uses Postgres; leave it empty and it uses SQLite at `DB_PATH`. It wins when both are set, so a cutover — and its rollback — is one variable rather than a different build. Postgres is what more than one instance needs: SQLite allows exactly one writer and wants a local block device, never NFS or SMB |
| `REQUIRE_POSTGRES` | unset | `1` refuses to start unless the database is Postgres, so a `DATABASE_URL` that fails to arrive stops the container instead of opening an empty SQLite file. `deploy/gcp/cloudrun.sh` sets it with `DATABASE_URL` |
| `DB_PATH` | `attesttag.db` | SQLite file. `/data/attesttag.db` in the container image; set `testing.db` in `.env.testing` so local runs keep their own rows |
| `DOCS_S3_URL`, `DOCS_S3_KEY_ID`, `DOCS_S3_SECRET` | unset | `s3://bucket/prefix?endpoint=https://…&region=auto` puts documents in any S3-compatible store — AWS S3, Cloudflare R2, MinIO, Spaces, B2, Wasabi — which is what a platform with no persistent disk or no FUSE mount needs. Each organisation's documents go under `<prefix>/org-<id>/`. Region defaults to `us-east-1` when left off; R2 wants `auto`. Wins over `DOCS_BUCKET`. It also replicates the SQLite database into the same bucket, unless `DATABASE_URL` is set |
| `DOCS_DIR` | `docs` (`/app/docs` in the container image) | where documents live when no bucket is named, one folder per organisation (`org-<id>/`), indexed for `search_docs` |
| `DOCS_BUCKET`, `DOCS_PREFIX` | unset, `docs` | a GCS bucket for documents instead, which is what `deploy/gcp/cloudrun.sh` sets. Uploads, listing and indexing all go through its API, under `<prefix>/org-<id>/` |
| `MAINTENANCE` | unset | `1` is the cutover freeze: Slack and Teams deliveries are acknowledged and dropped, Stripe's are refused so they are sent again, no background loop starts (routines, investigations, document indexing), and the console says so. See `deploy/docs/postgres-cutover.md` |

#### Replicating the SQLite database

| variable | default | purpose |
|---|---|---|
| `LITESTREAM_S3_URL`, `LITESTREAM_S3_KEY_ID`, `LITESTREAM_S3_SECRET` | unset | a bucket of its own for the SQLite replica, when the database should not share the documents' one. **Not needed to get replication**: `DOCS_S3_URL` already replicates the database into that bucket at `<prefix>/LITESTREAM_PATH`. The keys fall back to `DOCS_S3_KEY_ID` and `DOCS_S3_SECRET` |
| `LITESTREAM_BUCKET`, `LITESTREAM_PATH` | unset, `litestream/attesttag.db` | a GCS bucket for the replica instead, which is what `deploy/gcp/cloudrun.sh` sets, and the key within whichever bucket is used — except a `LITESTREAM_S3_URL` with a path, whose path is the key and which ignores `LITESTREAM_PATH`. The single-writer lease lives beside it at `<path>.lock.json`; no bucket anywhere means no replication and no lease, and the database is the local file |
| `LITESTREAM_BIN` | `litestream` | the Litestream binary, when it is not on `PATH` |
| `LITESTREAM_CONFIG` | unset | a `litestream.yml` of your own. Unset means the one rendered at startup for the bucket that was resolved |

### The model

| variable | default | purpose |
|---|---|---|
| `LLM_BASE_URL` | `https://openrouter.ai/api/v1` | any OpenAI-compatible endpoint |
| `LLM_MODEL`, `HEAVY_MODEL`, `EMBED_MODEL` | `z-ai/glm-5.3-flash`, `z-ai/glm-5.3`, `qwen/qwen3-embedding-8b` | default models (console overrides) |
| `DENY_TRAINING` | `1` | OpenRouter: only providers that do not train on prompts |
| `PROVIDER_SORT`, `PROVIDER_ORDER` | `price`, unset | OpenRouter's provider routing: which of a model's endpoints answers. A sort (`price`, `throughput`, `latency`) pins one, which keeps the prompt cache warm across a turn's rounds; `none` leaves OpenRouter's load balancing on. The order, comma separated, names providers to try first. Fallbacks stay on either way |
| `REASONING` | `low` | reasoning effort sent with every completion (`minimal`, `low`, `medium`, `high`), always with `exclude` so thinking never reaches Slack. `none` switches reasoning off for models that allow it; some endpoints refuse to run without it. On OpenAI's own API it is sent as `reasoning_effort` to the models that reason (anything below `medium` as `low`) and not at all to the rest |
| `ORG_MODEL_KEYS` | `all` | which organisations may bring their own model key under Settings → Models: `all`, `enterprise` (only accounts on the enterprise plan — what the hosted service runs) or `off`. A typo reads as `enterprise` and is logged. See [Its own model key](plans.md#its-own-model-key) |

What each endpoint is sent follows its host. `openrouter.ai` gets OpenRouter's fields — reasoning,
provider routing, prompt-cache markers. `api.openai.com` and Azure OpenAI (`*.openai.azure.com`,
`*.cognitiveservices.azure.com` and `*.services.ai.azure.com`) get none of them, the system prompt
as one string, a temperature only on the older chat models and `reasoning_effort` only on the
models that reason, because OpenAI refuses the first field it does not know. `LLM_BASE_URL` on any
other host keeps OpenRouter's shape, as it always has, since a gateway in front of OpenRouter may
depend on it. Every completion the bot asks for, on every host, asks for at most 32,768 tokens of
output.

### HTTP server and public origin

| variable | default | purpose |
|---|---|---|
| `HEALTH_ADDR` / `PORT` | `:8080` | listen address for console, API, and health |
| `ADMIN_BASE_URL` | unset | pins the public origin behind every link the bot builds — reply footers, setup links, verification, reset and invitation mail, the worker callback — every sign-in redirect, and the MCP server's OAuth addresses. Unset, the bot learns it from the first sign-in or signed-in console request on a host that is not loopback, keeps it as the `public_origin` setting, and afterwards lets only that host change it (or, with `PUBLIC_ORIGIN_HOSTS` set, only the hosts it names). A Slack or Microsoft sign-in started on any other address is sent to that origin first, and single sign-on started there is refused with the address to use. Until an origin is learned, links and sign-in redirects point at `http://localhost:<port>`, which works only on the bot's own machine |
| `PUBLIC_ORIGIN_HOSTS` | unset | with `ADMIN_BASE_URL` unset, the hosts (comma separated) the bot may learn its public origin from. Unset, the first host a sign-in or signed-in console request arrives on is kept, and only that host may change it |
| `TRUST_PROXY` | unset | whether `X-Forwarded-For` names the caller, for the sign-in and two-factor lockouts, the signup, reset, checkout and operator limits and the address in the audit log. Unset, it is believed from a private or loopback peer and on Cloud Run, and ignored from a public one. `1` always believes it, for a proxy that reaches the bot from a public address; `0` never does. The rightmost address is the one read |
| `HEALTH_SECRET` | unset | `/health` answers `ok` to everyone. Set it and a caller sending it in an `X-Health-Secret` header also gets the writer state, the workspace, document and chunk counts and the month's spend — everyone else still gets `ok`. `?secret=<this>` works too, but a query string ends up in access logs |
| `SITE_URL` | unset | this deployment's public website, if it has one: the console's Get started page fetches its recorded walkthroughs from there, and it is the one cross-origin the console's CSP allows. It also names the website, privacy and terms links in the Teams app package (`<SITE_URL>/privacy`, `/terms`); unset, those point at the console's own origin. Empty means the console talks to its own origin and nothing else, which is what a self-host wants |

### Behaviour defaults

Where the purpose names a console setting, that setting overrides the variable once saved.
`TURN_MAX_MINUTES`, `TURN_MAX_USD` and `INVESTIGATION_WORKERS` have none: they are the operator's.

| variable | default | purpose |
|---|---|---|
| `BOT_NAME`, `TZ_NAME` | `attest_tag`, `America/New_York` | name and timezone defaults (console: `bot_name`, `timezone`). A new organisation takes the zone its founder signed up from, so `TZ_NAME` only answers for the ones that have none |
| `MONTHLY_BUDGET_USD`, `HISTORY_LIMIT`, `MAX_TOOL_ROUNDS` | `20`, `40`, `50` | console: `monthly_budget_usd`, `history_limit`, `max_tool_rounds`. Budget `0` = the plan's ceiling, or unlimited when there is none. A channel can raise `MAX_TOOL_ROUNDS` for itself on its Configure page, up to 80; nothing gives a reply more than 80 rounds |
| `TURN_MAX_MINUTES` | `12` | ceiling on one reply's wall clock. A reply's own deadline follows the rounds it may spend (20s each, at least two minutes), so raising a channel's rounds gives it the clock to use them. Investigations and routines run on clocks of their own (`investigation_minutes`, `routine_minutes`, up to an hour), which this does not shorten |
| `TURN_MAX_USD` | `0.50` | the most one turn — a reply, an investigation or a routine run — may spend before its tools are taken away and it writes up what it has; `0` switches it off. Where a provider reports no cost, eight million prompt tokens stands in |
| `ROUTINE_ROUNDS`, `ROUTINE_MINUTES` | `200`, `30` | what one scheduled run is given, held to 1–200 rounds and 2–60 minutes. Console: `routine_rounds`, `routine_minutes` |
| `INVESTIGATION_WORKERS` | `2` | investigations this container runs at once, across every organisation. `0` switches the lane off here; queued questions then wait for a container that runs one |

### Who may use it

| variable | default | purpose |
|---|---|---|
| `SIGNUP_MODE` | `first-run` | who may create an account. `first-run`: the first sign-up founds the deployment and everybody after arrives by invitation. `open`: anyone who can reach the console may found their own organisation — what holds the door then is the tenant boundary, not the door, so set this only if you meant to run a service for strangers. `closed`: never, not even to bootstrap. Any other value reads as `first-run` and is logged |
| `ALLOWED_EMAIL_DOMAINS` | unset | the default for who the bot answers, in Slack and in Teams, by email domain, for an organisation with no list of its own. Each organisation's list under Settings → Security replaces it, and a new organisation starts with its founder's domain unless that is a public mail provider. With neither, any member of the workspace; guests and external (Slack Connect / other-tenant) accounts are refused unless `allow_external_users` is on. In Slack it needs the `users:read.email` bot scope |
| `ACCESS_TTL` | `168h` | How long an access request waits for an answer |
| `ACCESS_ALLOW_SELF_APPROVE` | `0` | `1` lets a requester approve their own request. Testing only — it is announced in the thread and marked on the record |

### Ceilings, plans and per-organisation limits

Sized for a deployment with open signup. Behind an invitation they are mostly in the way — see
[Plans and the operator API](plans.md), which is off by default.

| variable | default | purpose |
|---|---|---|
| `PLATFORM_MONTHLY_BUDGET_USD_PER_ORG`, `PLATFORM_MAX_INFLIGHT_PER_ORG` | `0` (no ceiling), `8` | the operator's ceiling on what one organisation may spend a month on the deployment's key, free accounts included, and on the turns it may have running at once on one instance (`0` is no cap). No tenant setting lifts either. A plan granted with its own budget is held to that instead; an enterprise account, a pro account paying by credit, and an organisation on its own model key are not held to the first. Set it on a deployment that lets strangers sign up: without it, a tenant that puts `monthly_budget_usd=0` has no limit on the shared key |
| `FREE_PLAN_BUDGET_USD` | `0` | what a free-plan account may spend in a month, whatever its own budget setting says. `0` — the default — means no free-plan cap, leaving free accounts under `PLATFORM_MONTHLY_BUDGET_USD_PER_ORG` like everybody else |
| `SUPPORT_EMAIL` | unset | where a capped account is told to write, and where the console's Help button (the ? in the header) mails the questions typed into it, with the asker as Reply-To. Empty means this deployment publishes no address: budget refusals say the budget is fixed without naming anyone, and neither the Upgrade button nor Help is offered. On a deployment that sells plans from the console that button is replaced by Settings → Billing, leaving this address as where a refund is asked for. Never leave somebody else's address here |
| `OPERATOR_SECRET` | unset | at least 16 characters. Bearer secret behind `/api/operator/` and the `/operator` pages, which list accounts, move them between plans, grant credit and set enterprise deals. Unset or shorter, those routes do not exist |

#### Self-serve billing

| variable | default | purpose |
|---|---|---|
| `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` | unset | self-serve billing ([`billing.md`](billing.md)). Both or neither: with one set the other missing, billing switches itself off at startup, because a service that can charge a card and cannot hear the result must not charge one. Unset, the billing routes answer 404 and no account has a credit floor |
| `STRIPE_SIZES` | unset | the plan sizes a Pro fee is set by: `size=<price id>:<minor units>[:<included minor units>]`, comma separated, in the order to offer them. The optional third figure is the model credit the size includes each paid month. A size with no entry is not sold; one with no price id (`over_250=:0`) is listed as Talk to us and refused at checkout. `STRIPE_BANDS`, the old name, is read when this is unset |
| `BILLING_CURRENCY`, `BILLING_TOPUP_MIN_USD`, `BILLING_TOPUP_MAX_USD` | `usd`, `25`, `10000` | what credit is held in, and one top-up's bounds. Enforced server-side; an amount from a browser is never trusted |
| `BILLING_LOW_BALANCE_USD` | `10` | warn the account — in its alert channel and by mail, once per 72 hours — at this much credit left |

#### Per-organisation limits

| variable | default | purpose |
|---|---|---|
| `LIMIT_SIGNUPS_PER_IP_PER_HOUR`, `LIMIT_INVITES_PER_ORG_PER_HOUR`, `LIMIT_INVITES_PER_ADDRESS_A_DAY` | `5`, `20`, `3` | what stands between a stranger with a script and your mail domain |
| `LIMIT_EMAIL_TURNS_PER_CHANNEL_PER_HOUR` | `12` | how many forwarded emails one channel may turn into a turn in an hour. An address anyone can mail needs a ceiling that binds before the spending, not after: the per-organisation limits are counted from usage rows written once a turn has already run |
| `LIMIT_EMAIL_AUTO_WRITES_PER_TURN` | `3` | how many writes one forwarded mail may run unattended, on a channel that has switched *allow rules on forwarded email* on. A value that is not a positive number is refused and logged rather than silently applied |

### Fix worker

Off unless `WORKER_MODE` says otherwise. See [Fix jobs](fix-jobs.md).

| variable | default | purpose |
|---|---|---|
| `WORKER_MODE` | `off` | `off` (tool not offered), `workers`, or `local` (subprocess `attesttag worker`, for development). `workers` runs each job in a container of its own and detects the platform from `KUBERNETES_SERVICE_HOST`, `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI` or `AWS_CONTAINER_CREDENTIALS_FULL_URI`, `CONTAINER_APP_NAME`, `K_SERVICE` or a Docker socket, logging which at boot; if none of them says where it is, it stays off rather than guessing. Naming a platform directly — `cloudrun`, `ecs`, `aca`, `k8s`, `docker` — pins it. Anything else is refused and treated as `off`. The bot's public origin must be https in every mode but `local`, since the worker calls back to it |
| `WORKER_JOB_NAME`, `WORKER_PROJECT`, `WORKER_REGION` | `attesttag-worker`, metadata, `us-central1` | the execution the platform starts: a Cloud Run job, an ECS task definition, a Container Apps job. In `ecs` mode `WORKER_REGION` falls back to `AWS_REGION`, then `AWS_DEFAULT_REGION`, never to `us-central1` |
| `WORKER_IMAGE` | unset | on `k8s` and `docker` only, where there is no job object to name and the bot writes the whole pod spec. Required in those two, where `WORKER_JOB_NAME` wins over it when set and a `WORKER_JOB_NAMES` value is an image too |
| `WORKER_CPU`, `WORKER_MEMORY` | `2`, `4Gi` | per job, in the same two modes. Elsewhere the job or task definition carries it |
| `WORKER_JOB_NAMES` | empty | route a repository to a heavier worker by the ecosystem an earlier job or a recipe recorded for it, e.g. `java=attesttag-worker-jvm,java-gradle=attesttag-worker-jvm,dotnet=attesttag-worker-jvm` (`java-gradle` and `java-maven` also answer to `java`). Each value is a job or task definition, or on `k8s` and `docker` an image; anything not named runs on `WORKER_JOB_NAME` |
| `WORKER_CACHE_BUCKET`, `WORKER_CACHE` | `LITESTREAM_BUCKET`, on | the GCS bucket the per-repository dependency cache lives in, handed to each job as signed URLs, and `off` to do without it |

#### Fix worker keys and the worker's own environment

| variable | default | purpose |
|---|---|---|
| `OPENROUTER_PROVISIONING_KEY` | unset | OpenRouter management key: a per-job key capped at the job budget, exact spend read back. Without one, jobs run on the shared key, uncapped — except where `SIGNUP_MODE=open`, where a fix job is refused rather than hand a stranger's repository code the shared key. An organisation on its own model key runs its jobs on that key or not at all |
| `WORKER_LLM_BASE_URL`, `WORKER_LLM_API_KEY` | the bot's | model endpoint and shared key handed to the worker when no per-job key can be minted — never on a deployment with `SIGNUP_MODE=open` |

### GitHub App (optional)

Lets somebody install a GitHub App on their repositories from the console instead of pasting a
personal access token. Unset all of these and the flow is not offered; repositories are
connected with a token as before.

| variable | default | purpose |
|---|---|---|
| `GITHUB_APP_ID`, `GITHUB_APP_SLUG` | unset | the app's id, and the name in its install URL (`github.com/apps/<slug>`). Both public |
| `GITHUB_APP_PRIVATE_KEY_B64` or `GITHUB_APP_PRIVATE_KEY` | unset | the `.pem`, base64-encoded (preferred — a PEM is 28 lines, this file is read one line at a time, and base64 has no commas for `--set-env-vars` to split on) or raw with its newlines escaped |
| `GITHUB_APP_CLIENT_ID`, `GITHUB_APP_CLIENT_SECRET` | unset | the OAuth client, needed only to offer the Install button |

A **half**-configured app is a startup error on purpose: the alternative is a console showing an
Install button that leads to a 500. Set the id, the slug and a key together, or none of them.
The OAuth client is the exception — without it, existing installations keep working and only the
button is hidden.

### Microsoft Teams (optional)

The same bot in Teams channels and chats, beside Slack. Unset all of these and Teams is not
offered; set them and the Workspaces page gains **Add workspace → Microsoft Teams**, which hands
out the app package and a link code. [msteams.md](msteams.md) is the whole setup.

| variable | default | purpose |
|---|---|---|
| `MSTEAMS_APP_ID` | unset | the Azure Bot's Microsoft App ID. Public: it is in the app package every tenant installs |
| `MSTEAMS_APP_PASSWORD` | unset | a client secret of that app registration. The only secret among these |
| `MSTEAMS_TENANT_ID` | unset | the directory the app registration lives in. Required for `SingleTenant`, where tokens are minted there |
| `MSTEAMS_APP_TYPE` | `SingleTenant` | `SingleTenant` or `MultiTenant` — whatever the Azure Bot resource says it is |
| `MSTEAMS_SIGNIN` | unset | Sign in with Microsoft to the console: `organizations` for any work or school account, or one tenant id. Unset, the button is not offered. Needs `<origin>/api/auth/microsoft/callback` registered as a Web redirect URI on the same app registration |

As with the GitHub App, **half** a configuration is a startup error: an id without a password is
a bot that hears every message and cannot answer one.

### Per-channel settings

A channel's own settings (instructions, default model, default repository, read every message,
email intake, tool rounds, budget, member edits, attached bundles and one-off connections, channel
allow rules) live on the Workspaces page of the console and on the channel's Configure page.

One of them is its own decision and worth naming here: **allow rules on forwarded email**
(`email_auto_writes`, `inherit | on | off`, off everywhere until asked for, inherited like
`email_intake`). A turn a forwarded mail starts holds every write, whatever the rules say, because
nobody in the workspace wrote the mail; this is the channel saying it means its rules for mail too.
What it lifts is narrow on purpose — the rule is judged on where the write goes and never on the
body, a fix job is never covered, the turn gets `LIMIT_EMAIL_AUTO_WRITES_PER_TURN` of them, and each
is recorded as `write.auto_ran` with the rule that allowed it.

## Documents

Each organisation's documents live in a folder of its own, `org-<id>/` under `DOCS_DIR` (`docs/`
by default) or under the bucket's prefix — `org-1/` for the first organisation a deployment
founds. Upload them in the console, or drop `.md`, `.markdown`, `.txt`, `.rst`, `.pdf`, `.html`,
`.htm`, `.csv`, or `.json` files into that folder, and they are indexed on start, every six hours,
on `!ingest`, or on console reindex. Each document can be scoped to the whole workspace or to one
channel. A PDF whose text runs past 32 MiB, or that takes `pdftotext` more than a minute, is
refused rather than indexed.

A file at the top of `docs/` belongs to no organisation and is never indexed. That includes the
four small sample documents the repository ships there (expense policy, refund policy, release
process, and a prompt-injection test file): the live evals' document questions expect them, so
copy them into the evaluating organisation's folder first.

Documents can live in folders. Subfolders of an organisation's folder are indexed like anything
else, and the console can make a folder, drop or pick a whole folder to upload (its shape is
kept), and move a document or a folder somewhere else. A folder is only a prefix of a document's
path, so it changes nothing about retrieval — it is for the people looking after the corpus. Empty folders
are the one thing a path cannot express on its own, so those are remembered in
`document_folders`. Dot files and dot folders are never uploaded or indexed.

A folder in Google Drive can be mirrored into the corpus and kept in step with it, on a
service-account credential: [Drive sync](google.md#drive-sync). `LIMIT_DRIVE_SYNCS_PER_ORG`
caps how many folders one organisation may follow.
